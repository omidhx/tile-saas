# Wireframe متنی — UX نماینده

> قدمِ «wireframe متنی UX» از spec بخش ۱۳. مرجع قوانین: بخش ۱۰ (UX نماینده) و بخش ۱۱ (معماری React).
> این سند **قرارداد رفتاری** است، نه فقط چیدمان — هر صفحه به قانونی که enforce می‌کنه لنگر خورده.
> موبایل-فرست؛ حداکثر ۳ کلیک تا ثبت سفارش. صفحه‌های staff/انباردار جدا هستن و اینجا نیستن.

## اصل‌ها (روی همه‌ی صفحه‌ها)
- **Findability > زیبایی** — نماینده در < ۳۰ ثانیه بفهمه جنس هست یا نه.
- **`bin_location` هرگز در UI نماینده** — فقط پنل staff. برای نماینده نویزه.
- **قیمت هر نماینده فقط مال خودش** — نماینده‌ها قیمت هم رو نمی‌بینن (spec ۵.۷).
- عددِ موجودی که نماینده می‌بینه = `available` (قابل‌سفارش)، نه `on_hand`.

## ۱. داشبورد (خانه)

```
┌────────────────────────────────────────────┐
│ 🔍 [ جستجوی سریع: نام، کد، ابعاد…        ] │
│ فیلتر: [ابعاد▾][رنگ▾][درجه▾][انبار▾][قیمت▾]│
├────────────────────────────────────────────┤
│ ┌────────┐┌────────┐┌────────┐┌────────┐  │
│ │قابل‌سفارش││رزروهای ││سفارش‌های││ هشدارها ││  │
│ │  امروز  ││   من   ││   باز  ││   ۳    ││  │
│ │  ۱٬۲۴۰  ││   ۵    ││   ۲    ││ 🔔     ││  │
│ └────────┘└────────┘└────────┘└────────┘  │
├────────────────────────────────────────────┤
│ کالاهای پرتکرار تو  ▸ (کارت‌ها، بخش ۲)     │
└────────────────────────────────────────────┘
```
- ۴ کاشیِ بالا = میان‌بر، هرکدوم به لیستِ فیلترشده لینکه.
- «رزروهای من» شمارنده‌ی TTL داره (صفحه ۵).
- «هشدارها» = `StockAlert`هایی که دوباره موجود شدن.

## ۲. کارت کالا (نتیجه‌ی جستجو / لیست)

```
┌──────────────────────────────┐
│ [عکس]  گرانیت مشکی براق       │
│        کد: GB-6060   درجه ۱   │
│  قابل‌سفارش: ۴۸ کارتن          │
│           (معادل ۱۰۲٫۲۴ متر)  │  ← شفافیت رند (بخش ۱۰): عددِ واقعی، نه گردشده
│  قیمت من: ۲٬۳۵۰٬۰۰۰ ریال/متر  │
│  [ رزرو ]  [ سفارش ]  [مشابه‌ها]│
└──────────────────────────────┘
```
- «قابل‌سفارش» از `v_lot_availability` (نه `on_hand`).
- اگه `available = 0`: دکمه‌ی رزرو غیرفعال، «مشابه‌ها» پررنگ (وصل به فیچر کالای جایگزین).
- «مشابه‌ها» → همون Variant با شید/کالیبر دیگه، یا محصولِ نزدیک.

## ۳. جزئیات کالا + انتخاب Lot (رزرو)

```
┌────────────────────────────────────────┐
│ گرانیت مشکی براق — GB-6060  درجه ۱      │
├────────────────────────────────────────┤
│ Lotها (قابل‌سفارش):                     │
│  ○ بچ B-١٠٢  شید A  کالیبر ٢  — ۳۰ کارتن│
│  ○ بچ B-١١٧  شید A  کالیبر ٢  — ۱۸ کارتن│
│  ○ بچ B-٠٩٨  شید C  کالیبر ٢  — ۹۶ کارتن│
│                                        │
│ تعداد: [   ] کارتن   [ افزودن به سبد ]  │
└────────────────────────────────────────┘
```
- ستون شید/کالیبر فقط وقتی `track_shade_caliber ≠ off` نشون داده می‌شه (بخش ۷.۱).
- **هشدار مخلوط شید** (بخش ۷.۲): اگه کاربر از دو شیدِ متفاوتِ یک Variant به سبد اضافه کنه:
  > ⚠️ «شید A و C متفاوت‌ان؛ برای یک سطح پیوسته توصیه نمی‌شه.» — هشدار نرم، نه منع.
- پیشنهاد پیش‌فرضِ Lot = FIFO روی `entry_date`، هم‌شید/هم‌کالیبر (بخش ۷.۴).

## ۴. سبد رزرو + ثبت  ← بحرانی‌ترین صفحه

```
┌────────────────────────────────────────┐
│ سبد رزرو (۲ قلم)                        │
│  • GB-6060  بچ B-١٠٢  — ۱۰ کارتن   [x]  │
│  • WM-3030  بچ W-٠٤١  — ۵  کارتن   [x]  │
├────────────────────────────────────────┤
│           [ ثبت رزرو (all-or-nothing) ] │
└────────────────────────────────────────┘
```
قوانین معماری React (بخش ۱۱) که این صفحه enforce می‌کنه:
- **سبد = state جدا (Zustand)، نه server state.** با submit موفق خالی می‌شه (بخش ۱۱.۴).
- **Pending state، نه Optimistic UI** (بخش ۱۱.۱): با کلیک ثبت → دکمه غیرفعال + spinner inline. هیچ «موفقیت»ی قبل از تأیید سرور نشون داده نمی‌شه.
- **بدون Refetch-before-submit** (بخش ۱۱.۲): مستقیم `POST /api/reservations`. چکِ `available` کارِ بک‌انده، در کلاینت تکرار نمی‌شه.
- **رزرو all-or-nothing** — یا کل سبد یا هیچ (قانون معماری #۳).

**حالت باختِ رزرو (۴۰۹ Conflict)** — پیام دقیقِ بخش ۱۱.۵:
```
┌────────────────────────────────────────┐
│ این مقدار همین الان توسط نماینده‌ی دیگه  │
│ رزرو شد. موجودی فعلی: ۳ کارتن.          │
│   [ رزرو ۳ کارتن ]   [ دیدن مشابه‌ها ]  │
└────────────────────────────────────────┘
```
- در React Query، `onError` کش رو invalidate می‌کنه و همین پیام هوشمند رو می‌سازه.

## ۵. رزروهای من

```
┌────────────────────────────────────────┐
│ رزروهای فعال                            │
│  • GB-6060 ×۱۰  ⏳ ۱۸:۳۲ مونده  [تبدیل] │
│  • WM-3030 ×۵   ⏳ ۲:۱۰  مونده  [تبدیل] │  ← نزدیک انقضا: قرمز
├────────────────────────────────────────┤
│ منقضی/لغوشده  ▸ (جمع‌شده)               │
└────────────────────────────────────────┘
```
- شمارنده از `expires_at`. وقتی گذشت، worker بوک‌کیپینگ status→expired (تأخیرش بی‌اثر روی درستیِ available — بخش ۵.۳).
- «تبدیل» → شروع `SalesRequest` (تأیید تجاری). خودِ Dispatch فیزیکی رو staff می‌سازه، نه نماینده (بخش ۵.۶).

---

## مرزها (این‌ها در UI نماینده نیستن)
- ساختِ `SalesDispatch`، شماره‌ی حواله، `bin_location`، مشتری نهایی → پنل staff.
- حالت آفلاین: فقط مشاهده‌ی کاتالوگِ کش‌شده با «آخرین به‌روزرسانی: X پیش». **رزرو آفلاین ممنوع** — race condition تضمینی (بخش ۱۰/۱۱).
